# Judo Sub-Technique Classification from Video — MC3-18 (RGB-only)

Reproducibility package (code, data, and trained models) for the video classification of
judo throws into **Sutemi-waza** vs **Tachi-waza**. Temporal model **MC3-18**, **RGB-only**
input, evaluated with **source-wise cross-validation** (StratifiedGroupKFold, leakage-free).

This is the companion repository for the paper *"Automatic Classification of Judo
Technique from Video: An Industry-Academia Collaboration"*.

## Main result

| Model (RGB-only, 10-fold source-wise CV) | Macro F1          |
| ----------------------------------------- | ----------------- |
| **MC3-18**                                | **0.787 ± 0.027** |
| MC3-18, two-stream (RGB + optical flow)   | 0.781 ± 0.038     |
| R(2+1)D-18                                | 0.582 ± 0.083     |
| R(2+1)D-18, two-stream                    | 0.639 ± 0.073     |

The reported number is the **cross-validation mean**, not the best fold (avoids
cherry-picking). Per-fold breakdown in
[`results/cv_summary.md`](results/cv_summary.md) (generated by `scripts/04_cv_summary.py`).

**RGB-only was selected over two-stream** (RGB + optical flow) as the released
configuration: it matches or slightly exceeds two-stream's macro F1 for MC3-18, while
using half the parameters (11.49M vs 22.98M) and roughly half the inference time, and it
avoids the optical-flow extraction stage entirely. See the paper (RQ2/RQ3) for the full
analysis, including why optical flow *does* help R(2+1)D-18 but not MC3-18.

> **You get the trained model even though you can't fully reproduce the exact number.**
> The paper's `0.787 ± 0.027` was measured on the **full dataset** (2,070 clips: private
> footage from our industry partner + public YouTube sources). Only the **public** portion
> can be redistributed here (565 clips, 13 YouTube sources) — private data is never
> shipped in this repository. Because of that, **training or evaluating from scratch with
> only the public data in this repo will not reproduce `0.787 ± 0.027`**, and that's
> expected, not a bug: it's a smaller, differently-balanced sample. What *is* the exact
> production model is already sitting in [`results/models/mc3_18_rgb/`](results/models/mc3_18_rgb/)
> — **the 10 checkpoints released there are the very same weights used to compute the
> paper's official number**, trained on the full private+public dataset. Running them (via
> `scripts/05_classify_clip_ensemble.py`) on new clips, or on the public subset shipped
> here, uses the real model — only the *training data* is restricted, not the model
> itself. Evaluating the released ensemble on the public subset gives Macro F1 = 0.769
> (see [`results/public_subset_evaluation_summary.json`](results/public_subset_evaluation_summary.json))
> — a real, honest number for a smaller/different sample, not a discrepancy to be
> alarmed about.
>
> **All four rows of the table are auditable, not just the top one.** Every configuration
> has its full per-fold report released — `config.json`, `classification_report.json`,
> confusion matrices, and `predictions_test.csv` — under `results/models/<config>/foldN/`,
> so you can verify exactly how each number was computed even without retraining.
> Full checkpoints (`.pt`) are released for the two **RGB-only** configurations
> (`mc3_18_rgb/`, `r2plus1d_18_rgb/`); the two **two-stream** configurations
> (`mc3_18_two_stream/`, `r2plus1d_18_two_stream/`) ship reports only, to keep this
> repository's size reasonable — they were not selected for deployment (see RQ2/RQ3 in
> the paper), so redistributing their weights was a lower priority than the four-way
> report/audit trail.

> **Why source-wise cross-validation?** Many clips come from the same match/source
> (near-duplicates). With a per-video split, clips from the same match can land in both
> train **and** test, and the model memorizes the scene (inflated metric).
> `StratifiedGroupKFold` grouped by source guarantees that **no source crosses**
> partitions → an honest number. This is the main methodological safeguard in this work.

## 1) Environment

Requires a **CUDA GPU** to train (the model is a temporal 3D network); classification
with the released ensemble also runs on CPU (slower). Python 3.10.

```bash
# option A: pip
pip install -r requirements.txt
#   torch with CUDA: see the note at the top of requirements.txt

# option B: conda
conda env create -f environment.yml
conda activate judo-mc3
```

## 2) Data

This repository shares a **public subset** of the study's dataset (the full dataset,
larger and partly private, is described in the paper). The **source videos are not
redistributed** (channel copyright), but the **565 clips are fully regenerable** from the
manifest — **no need to contact the authors**.

The manifest [`data/input_data/video_sources.csv`](data/input_data/video_sources.csv) has
**one row per clip**, with the source video (`id`, `url`), the **cut interval**
(`cut_interval`), the `class`, and the clip's `filename`. The 565 clips come from **13
public YouTube sources**.

| Class (binary) | Composition                     | Clips   |
| --------------- | -------------------------------- | ------- |
| Sutemi-waza     | sutemi_waza                      | 128     |
| Tachi-waza      | ashi_waza (258) + te_waza (179)  | 437     |
| **Total**       | —                                 | **565** |

**To reconstruct the dataset** (no contact needed):

```bash
# (a) download the 13 source videos from the manifest URLs (720p)
python scripts/01_download_videos.py

# (b) cut the 565 clips at the manifest's exact intervals (requires ffmpeg)
python scripts/02_generate_clips.py
```

Clips are written to `data/analysis_data/clips/`, ready for training. The class is in the
filename; the source-wise split is generated during training (`--group_split`). Details
in [`data/README.md`](data/README.md).

## 3) Classify a clip with the released ensemble (no training needed)

The fastest way to use the released model: classify an already-cut ~4s clip (or several)
with the 10-fold ensemble.

```bash
python scripts/05_classify_clip_ensemble.py path/to/clip.mp4
# multiple clips, save results as JSON:
python scripts/05_classify_clip_ensemble.py clip1.mp4 clip2.mp4 --json out.json
```

This loads the 10 checkpoints in
`results/models/mc3_18_rgb/fold{0..9}/multiclass/best_model.pt` (default; pass
`--models-dir results/models/r2plus1d_18_rgb` for the other released config), samples 64
frames per clip using the exact same code path as training, runs each of the 10 models,
and averages the softmax probabilities (bagging-style ensemble) for the final prediction
and confidence. The clip must already be cut to the technique window (this script does
not detect or trim it for you).

## 4) Training (cross-validation, 10 folds)

```bash
# Linux (GPU):
bash scripts/03_train_cv_mc3.sh data/analysis_data/clips

# Windows (GPU):
powershell -ExecutionPolicy Bypass -File scripts\03_train_cv_mc3.ps1 data\analysis_data\clips
```

Each fold reproduces exactly the hyperparameters in
`results/models/mc3_18_rgb/foldN/config.json` (mc3_18, binary sutemi vs tachi, 64 frames,
112px, RGB-only, 40 fine-tuning epochs, seed 42, source-wise split, 10 folds). The other
three configurations in the main table (R(2+1)D-18 RGB, MC3-18 two-stream, R(2+1)D-18
two-stream) use the same command with `--model`/`--input_modality` changed accordingly —
see each config's `config.json` under `results/models/<config>/fold0/` for the exact
flags used.

## 5) Final CV number

```bash
python scripts/04_cv_summary.py      # prints and saves results/cv_summary.md
```

## 6) Reproducing the inference-cost benchmark (RQ3)

```bash
python scripts/06_benchmark_inference.py --config-dir results/models/mc3_18_rgb
python scripts/06_benchmark_inference.py --config-dir results/models/mc3_18_rgb \
    --config-dir results/models/r2plus1d_18_rgb
```

Reproduces the paper's Section V ("Inference Cost") numbers: loads all 10 checkpoints of
a configuration, times one full ensemble forward pass (all 10 models, batch size 1,
`num_frames`/`image_size` read from `config.json`) over several runs after a warm-up,
with `torch.cuda.synchronize()` around each timed section. **Requires a CUDA GPU** to
match the paper's numbers (measured on an NVIDIA L4); this benchmarks GPU compute only —
it does not include optical flow extraction (CPU-only, see `docs/methodology.md`) or
video I/O. Out of the box this only runs for the two configs whose checkpoints are
released (`mc3_18_rgb`, `r2plus1d_18_rgb`); the two-stream configs need their own
checkpoints placed under `results/models/<config>/foldN/multiclass/best_model.pt` first
(not redistributed here — see the note under "Main result" above).

## Throw-detection extractor (`dist/`)

The [`dist/`](dist/) folder ships a **standalone executable** (`detector_quedas`) that
detects throws in full videos via pose (YOLO). It's an **optional** helper for extracting
clips: you can use it **or** cut clips manually. Details in [`dist/README.md`](dist/README.md).

- **Overdetects:** being pose-based, it flags more throws than are actually there (e.g.,
  standing athletes bending over). Incorrect segments need to be **manually reviewed and
  discarded** — this is exactly why every automatically-extracted clip in this dataset went
  through manual review before being labeled (see the paper's data pipeline section).
- **Does not bundle** `torch`/`ultralytics` in the executable; it delegates to the system
  Python (you install `ultralytics` via `pip`). Ultralytics' official pose model is
  downloaded by it and is **not** redistributed here — only the project's own code ships
  with this package.
- Built and **tested on Linux** (ELF); not verified on Windows/macOS.
